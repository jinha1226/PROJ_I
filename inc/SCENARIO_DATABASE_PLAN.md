# 시나리오 데이터베이스 구축 방향

> 이 문서는 `inc/DESIGN.md`의 현재 게임 방향과 `inc/EVENT_SYSTEM_DIRECTION.md`의 사건 시스템을 보완한다. 기존 런타임 사건 시스템을 대체하는 문서가 아니라, 외부 어드벤처 시나리오를 분석·정규화해 재사용 가능한 콘텐츠 데이터로 만드는 별도 제작 파이프라인의 방향을 정한다.

- 상태: 설계 및 첫 원본 시나리오 분석 진행 중
- 첫 분석 대상: **The Old Blood** (Doomed Zone)
- 데이터 초안: `the_old_blood_source_db_v0.2.json` (현재 로컬 작업 산출물, 이 문서와 함께 저장소에 포함된 것은 아님)
- 기준일: 2026-11-05

---

## 1. 왜 시나리오를 데이터베이스화하는가?

### 1.1 콘텐츠를 매번 처음부터 만들지 않기 위해

어드벤처 시나리오 하나에는 단순한 퀘스트 줄거리만 있는 것이 아니다. 장소, 방 구조, 인물, 세력, 이해관계, 사건, 단서, 함정, 몬스터, 보상, 선택, 결과, 시간에 따른 세계 변화가 함께 들어 있다.

이를 원문 문서 단위로만 보관하면 다른 시나리오를 만들 때마다 내용을 다시 읽고 처음부터 설계해야 한다. 반대로 요소를 일정한 데이터 구조로 추출하면 다음과 같이 재사용할 수 있다.

- 한 시나리오의 장소와 다른 시나리오의 사건 구조를 조합한다.
- 인물의 목표·비밀·관계를 다른 지역이나 세력에 맞게 재구성한다.
- 특정 사건을 다른 방 태그, 파티 상태, 층 진행도에 맞춰 변형한다.
- 단서와 결과 구조를 재사용해 새로운 미스터리나 연속 사건을 만든다.
- 기존 몬스터·함정·보상 데이터와 연결해 실제 게임 규칙으로 변환한다.

즉, 시나리오를 데이터베이스화하는 목적은 원작을 통째로 게임에 넣는 것이 아니라, **시나리오 안에 들어 있는 설계 요소를 분해해 재사용 가능한 콘텐츠 자산으로 만드는 것**이다.

### 1.2 절차적 생성에 맥락과 인과관계를 공급하기 위해

현재 게임에는 방 태그, 사건 슬롯, 후보 필터링, 가중치 추첨, 사건 상태, 연속 사건을 처리하는 런타임 구조가 있다. 이 구조는 사건을 어디에 배치할지 결정할 수 있지만, 그 자체만으로 풍부한 이야기의 원인과 결과를 만들어 주지는 않는다.

시나리오 DB는 런타임 생성기에 다음 재료를 공급한다.

- 공간: 어떤 장소와 방이 존재하며 서로 어떻게 연결되는가?
- 행위자: 누가 무엇을 원하고, 무엇을 알고, 누구와 대립하는가?
- 원인: 어떤 사건이 왜 일어났는가?
- 단서: 플레이어가 그 원인을 어떤 경로로 알아낼 수 있는가?
- 선택: 플레이어가 어떤 위험과 대가를 감수할 수 있는가?
- 결과: 선택과 방치가 세계 상태와 후속 사건을 어떻게 바꾸는가?

따라서 목표는 무작위 이벤트를 많이 섞는 것이 아니다. **공간·인물·사건·단서·결과가 서로 설명되는 조합을 생성하는 것**이다.

### 1.3 매 원정에 다른 이야기가 생기게 하기 위해

게임의 핵심 원칙은 기존 설계와 같이 유지한다.

> 플레이어는 무엇을 감수할지 결정하고, 용병단은 그 결정을 실행한다.

일반 이동·전투·수집은 자동으로 처리하고, 의미 있는 위험과 보상, 구조, 거래, 갈등, 의식, 보스 상황에서 판단을 제공한다. 시나리오 DB는 이 판단 순간을 풍부하게 만드는 재료다.

같은 지역이라도 다음 요소가 달라지면 다른 원정이 된다.

- 어떤 인물과 세력이 살아남아 있는가?
- 어떤 단서가 먼저 발견되었는가?
- 누가 구조되거나 버려졌는가?
- 어떤 사건을 방치했고 어떤 사건에 개입했는가?
- 후속 사건이 준비되었는가, 지연되었는가, 실패했는가?
- 세계의 위기 단계가 어디까지 진행되었는가?

이 차이를 데이터로 기록하고 조합하면, 정해진 대본을 반복하는 대신 원정마다 다른 사건의 연쇄를 만들 수 있다.

## 2. 무엇을 데이터로 추출할 것인가?

시나리오를 하나의 긴 줄거리로 저장하지 않는다. 아래 단위로 나누고 서로 ID로 연결한다.

| 데이터 단위 | 저장할 핵심 정보 | 게임에서의 용도 |
|---|---|---|
| 세계·배경 | 시대, 지역, 역사, 현재 위기, 분위기 | 시나리오의 맥락과 생성 제약 |
| 장소 | 장소 ID, 설명, 태그, 위험도, 출입 조건 | 지역·층·방 생성 |
| 공간 구조 | 방, 복도, 출입구, 연결 관계, 층위 | 맵 토폴로지와 이동 경로 |
| 인물 | 정체, 역할, 목표, 비밀, 지식, 소속, 상태 | NPC 생성 및 반응 |
| 세력 | 목표, 자원, 적대·협력 관계, 영향력 | 세력 간 동태와 갈등 |
| 사건 | 발동 조건, 참여자, 선택지, 판정, 결과 | 런타임 이벤트 |
| 단서 | 발견 위치·방법, 내용, 신뢰도, 연결되는 사실 | 미스터리와 추론 |
| 함정·위험 | 발동 조건, 탐지·회피 방법, 피해·후속 상태 | 탐험 콘텐츠 |
| 조우·몬스터 | 등장 조건, 전투 역할, 변형 정보 | 자동 전투 콘텐츠 |
| 보상·유물 | 획득 조건, 효과, 비용, 희귀도 | 보상 및 성장 연결 |
| 세계 상태 | 단계, 타이머, 카운터, 플래그, 변화 규칙 | 시간에 따른 세계 진행 |
| 이야기 연결 | 선행 조건, 후속 노드, 대체 경로, 종료 조건 | 인과적인 절차적 구성 |
| 라이선스·출처 | 원본, 저자, 페이지, 라이선스, 제3자 자료 | 사용 가능 범위와 추적 가능성 |

모든 항목에 동일한 세부 수준을 강요하지 않는다. 원본에서 확인된 사실, 원본의 요약, 게임용으로 새로 해석한 내용, 아직 추출하지 않은 내용을 구분한다.

## 3. 원본과 게임 데이터를 분리한다

가장 중요한 원칙은 **원본에서 확인한 사실과 게임을 위해 새로 만든 해석을 섞지 않는 것**이다.

각 콘텐츠는 다음 네 층으로 관리한다.

1. **Source — 원본 근거**
   - 원문 표현 또는 충실한 요약
   - 문서명, 저자, 페이지
   - 원본 라이선스 및 제3자 자료의 권리 정보
   - 서로 모순되는 원문 정보와 불확실성 표시

2. **Normalized — 정규화 데이터**
   - 인물·장소·사건·단서 등을 공통 스키마로 정리
   - 고유 ID와 다른 항목을 가리키는 참조 ID
   - 원문에서 직접 확인되는 조건과 관계

3. **Adaptation — 게임용 변환**
   - 원본 규칙을 우리 게임의 자동 진행·전투·자원·시간 체계로 변환
   - 원본의 규칙을 그대로 유지하지 않는 경우 변경 이유 기록
   - 게임에 없는 능력·판정·보상은 새 규칙으로 명시

4. **Generated — 생성 결과**
   - 생성기가 선택·변형·조합한 실제 원정 콘텐츠
   - 사용한 원본 데이터 ID, 생성 시드, 선택된 분기와 상태 기록
   - 재현과 디버깅이 가능하도록 생성 결과 보존

이 분리는 원작의 사실을 잘못 바꾸거나, 게임용 추측을 원작의 공식 설정처럼 취급하는 일을 막는다.

### 3.1 출처와 신뢰도 표기

각 레코드는 최소한 다음 정보를 가진다.

- `id`: 안정적인 고유 ID
- `source_id`: 원본 시나리오 ID
- `source_pages`: 근거 페이지
- `extraction_status`: 미추출 / 요약 / 부분 추출 / 검증 완료
- `confidence`: 원문에서 직접 확인 / 문맥상 추론 / 게임용 제안
- `notes`: 모호함, 누락, 충돌, 검증 필요 사항

원문에 충돌이 있으면 임의로 하나를 선택하지 않는다. 충돌 내용을 둘 다 기록하고, 게임 구현에서 선택한 해석은 별도의 결정으로 남긴다.

## 4. 절차적 시나리오 생성 방향

### 4.1 무작위 조합이 아니라 제약이 있는 조합

서로 무관한 NPC, 장소, 사건을 무작위로 연결하면 설정은 다양해 보여도 이야기로서 납득하기 어렵다. 생성기는 아래 조건을 확인해야 한다.

- 장소 태그와 사건의 공간 조건이 맞는가?
- 인물의 목표와 행동이 서로 모순되지 않는가?
- 사건의 선행 조건이 충족되었는가?
- 인물이 알고 있는 정보만 말하거나 행동하는가?
- 단서가 실제로 발견 가능한 위치와 방법을 가지고 있는가?
- 핵심 사실을 알아낼 수 있는 대체 경로가 있는가?
- 선택 결과가 이후 세계 상태와 사건에 반영되는가?
- 파티 구성이나 특정 직업이 없어도 진행이 막히지 않는가?

가중치 추첨은 조건을 통과한 후보 사이에서만 수행한다. 조건에 맞는 후보가 없으면 사건을 억지로 만들지 않는다.

### 4.2 권장 생성 파이프라인

```text
원본 시나리오
    ↓
라이선스·출처 확인
    ↓
요소 추출 (장소 / 인물 / 세력 / 사건 / 단서 / 규칙)
    ↓
정규화 DB
    ↓
관계·인과 그래프 구성
    ↓
게임 규칙으로 변환
    ↓
공간·상태·파티 조건으로 후보 필터링
    ↓
제약을 만족하는 시나리오 조합 선택
    ↓
맵·NPC·사건·단서·보상 생성
    ↓
진행 가능성·인과관계·중복·라이선스 검증
    ↓
런타임 콘텐츠로 전달
```

### 4.3 이야기 그래프

이야기를 단순한 순서 목록으로 만들지 않는다. 노드는 사건·단서·상태 변화가 되고, 간선은 조건과 인과관계를 표현한다.

- 필수 선행 조건: 어떤 사실이나 사건이 먼저 있어야 하는가?
- 선택적 연결: 특정 선택을 했을 때만 열리는가?
- 시간 조건: 몇 층 뒤, 다음 원정, 특정 위기 단계에서 발생하는가?
- 실패·방치 경로: 플레이어가 무시하거나 실패해도 세계가 어떻게 진행되는가?
- 대체 단서 경로: 한 장소나 NPC를 놓쳐도 핵심 사실을 알아낼 수 있는가?
- 종료 조건: 해결, 실패, 방치, 지역 이탈 등 어떤 상태에서 끝나는가?

모든 이야기를 완주하도록 강제하지 않는다. 일부 인물의 생존이나 특정 사건의 성공을 필수 조건으로 만들지 않고, 세계가 플레이어의 행동과 무관하게 계속 변할 수 있게 한다.

### 4.4 원본 시나리오를 조합 가능한 콘텐츠로 바꾸는 예

원본에 다음 요소가 있다고 가정한다.

- 버려진 수도원
- 사라진 순례자
- 지하 제단
- 제단을 이용하려는 연금술사
- 제단의 정체를 암시하는 기록
- 의식이 진행될수록 강해지는 적

이를 그대로 하나의 퀘스트로만 사용하지 않는다. 장소·인물·단서·위기 타이머·선택·결과를 분리해 다른 지역에서도 쓸 수 있게 한다. 다만 제단과 연금술사의 관계처럼 해당 이야기의 고유한 인과관계는 연결 정보로 보존한다.

재사용은 요소를 아무렇게나 섞는다는 뜻이 아니다. 공통 구조는 재사용하되, 고유한 인과관계와 설정은 보존한다.

## 5. 첫 사례: The Old Blood

### 5.1 원본 개요

- 시나리오: **The Old Blood**
- 제작자: Doomed Zone
- 원본: 88페이지 PDF
- 공식 배포: https://doomedzone.itch.io/the-old-blood
- 배경: 과거 교역 중심지였으나 몰락한 브라넘(Brannam). 주민들은 살인 사건과 뱀파이어의 소문에 시달리고, 연금술사 Victor Marlowe와 지하의 Flooded Shrine, 봉인된 뱀파이어 군주 Edric von Braech가 위기의 축을 이룬다.

이 시나리오를 첫 사례로 고른 이유는 선형적인 퀘스트 진행만을 요구하지 않기 때문이다. 원문은 사건과 결말을 고정하지 않고, 인물의 생존 여부나 플레이어의 해결 방법이 달라질 수 있는 열린 구조를 제공한다. 따라서 절차적 이야기 생성에서 중요한 세계 상태 변화, 단서 발견, 인물의 이해관계, 시간에 따른 위기를 시험하기에 적합하다.

### 5.2 현재 데이터베이스 초안 현황

`the_old_blood_source_db_v0.2.json`에 다음 항목을 정리했다.

| 컬렉션 | 레코드 수 | 현재 수준 |
|---|---:|---|
| 장소 | 17 | 도시·구역·지하 공간 요약 |
| 인물 | 25 | 주요 인물 중심 요약 |
| 세력 | 6 | 목표와 역할 요약 |
| 사건 | 10 | 주요 사건·세계 변화 요약 |
| 시스템 | 6 | 원본의 시간·위기·판정 규칙 요약 |
| 조우 테이블 | 12 | 테이블 목록과 페이지 인덱스 |
| 몬스터 | 17 | 베스티어리 항목 목록 |
| 이야기 그래프 | 11 | 주요 흐름을 요약한 노드 |
| 지도 | 16 | 지도 이미지와 페이지 인덱스 |
| 변환 백로그 | 8 | 게임 적용을 위해 남은 작업 |

총 120개는 각 컬렉션 레코드 수를 합산한 값이다. 서로 다른 고유 개체 수를 뜻하지 않는다.

### 5.3 아직 완성된 DB가 아니다

현재 v0.2는 **시나리오 구조를 파악하고 후속 추출 작업을 계획하기 위한 1차 인벤토리**다.

아직 완료되지 않은 작업:

- Victor 미스터리의 단서와 발견 경로 전체 추출
- 조우 테이블의 각 행과 결과를 개별 레코드로 정규화
- 지도 이미지에서 방·출입구·연결 관계를 벡터/좌표 데이터로 추출
- 몬스터 능력치와 게임 전투 규칙의 대응 관계 정리
- 이야기 그래프의 모든 분기·실패·방치 결과 추출
- OCR이나 그림 판독이 불확실한 항목의 원본 페이지 재검증

따라서 현재 레코드 수를 콘텐츠 완성도나 게임에 바로 투입할 수 있는 이벤트 수로 해석하면 안 된다.

### 5.4 라이선스 주의

원본 PDF 88페이지의 라이선스 표기를 기준으로 구분했다.

- 시나리오의 원문 텍스트와 콘텐츠는 CC0 1.0으로 표시되어 있다.
- 일부 던전 지도 아트는 CC BY-NC 4.0으로 표시되어 있어 상업용 게임에 그대로 재사용하면 안 된다.
- Mark Gosbell의 지도 아트는 CC0 1.0으로 표시되어 있다.
- Watabou 지도 생성기는 PDF에서 개인·상업적 사용이 가능하다고 설명한다.
- 표지·배경의 DALL·E 2 생성 이미지 등은 실제 재사용 전에 해당 이미지의 출처와 적용 조건을 별도로 확인한다.

**실무 원칙:** 텍스트의 라이선스가 지도·일러스트·폰트 등 모든 첨부 자산의 라이선스를 대신하지 않는다. 상업용 빌드에는 권리가 확인된 자료만 넣고, 불명확한 지도는 직접 다시 만든다. 라이선스 판단은 원본 PDF의 p.88을 기준으로 기록했다.

### 5.5 확인된 원문 불일치 사례

살인 사건 발생표가 본문 p.6과 빠른 참조 p.86에서 서로 다르게 적혀 있다. 현재 DB는 이 차이를 `SYS-MURDER`와 `FLAG-001`에 기록했다. 어느 쪽이 최종 의도인지 확인되지 않았으므로 조용히 하나로 통일하지 않는다.

이런 불일치는 DB가 단순 요약본이 아니라 출처와 검증 상태를 보존해야 하는 이유다.

## 6. 현재 게임 사건 시스템과 DB의 관계

현재 `inc/EVENT_SYSTEM_DIRECTION.md`와 `inc/DESIGN.md`에는 런타임 사건 시스템이 기록되어 있다.

- 방 태그와 층의 사건 슬롯
- 공간·층·파티·상태 조건으로 후보 필터링
- 가중치 추첨과 최근 사건 중복 억제
- 시드 기반 재현과 지형 난수 분리
- 선택지·판정·결과 실행
- 연속 사건의 단계·旗标·후속 사건
- 파티 상태와 인물 구성에 따른 사건 변형

`inc/DESIGN.md` §98–100에는 사건 시스템, 방 태그와 연속 사건, 사건 콘텐츠 확장 작업이 기록되어 있다. 이 문서 작성 시점에 기록된 콘텐츠에는 SRD 함정, 위험·발견·조우·탐험·파티·대형 사건 유형과 연속 사건이 포함된다.

시나리오 DB는 이 런타임 엔진과 별개의 콘텐츠 제작·검증 계층이다.

| 구분 | 런타임 사건 시스템 | 시나리오 DB |
|---|---|---|
| 질문 | 지금 이 방에서 무엇이 발생할 수 있는가? | 어떤 이야기 요소와 인과관계를 제공할 것인가? |
| 책임 | 조건 평가, 후보 선정, 실행, 상태 기록 | 원본 추출, 구조화, 출처 관리, 관계·분기 보존 |
| 입력 | 정규화·게임화된 사건 데이터 | 원본 시나리오와 정규화 레코드 |
| 출력 | 실제 게임에서 발생하는 사건 | 재사용 가능한 콘텐츠 묶음과 생성 가능한 이야기 구조 |

DB를 만들었다고 기존 이벤트 엔진을 다시 만들지 않는다. 정규화된 사건을 기존 `G.Event`와 선택지·결과 구조에 연결하는 방향을 우선한다.

## 7. 앞으로 해야 할 일

### 1단계 — 첫 시나리오의 핵심 이야기 완전 분해

**우선순위: 가장 높음**

첫 검증 대상으로 Victor의 살인 사건 미스터리를 완성한다.

- Victor, Evelyn, Edric, Forgotten, Flooded Shrine의 관계를 명확히 기록
- 각 단서를 개별 레코드로 추출
- 단서의 실제 발견 위치·NPC·아이템·조건을 기록
- 사실 / 거짓 / 부분적으로 참 / 오해를 부르는 정보 구분
- 각 단서가 어떤 사실이나 인물의 정체를 뒷받침하는지 연결
- 단서 하나를 놓쳤을 때의 대체 발견 경로 확인
- Victor를 일찍 저지함, 도주함, Edric가 깨어남, 의식이 진행됨 등 상태별 결과 연결
- 원문 근거 페이지와 추론 여부 기록

이 작업으로 DB 스키마가 실제 미스터리를 표현할 수 있는지 검증한다.

### 2단계 — 원본의 모든 조우 테이블 정규화

- 12개 테이블의 모든 행을 개별 데이터로 추출
- 굴림 범위, 등장 조건, 결과, 참조 NPC·몬스터·장소를 연결
- 낮/밤, 거주/폐허 구역, 지하 공간 등 적용 범위를 태그로 표현
- 원본의 주사위 확률은 보존하되, 게임 가중치로 바꾼 값은 별도 필드에 기록
- 원문 표와 빠른 참조 사이의 불일치도 별도 플래그로 관리

### 3단계 — 지도와 공간 구조 데이터화

- 라이선스가 확인된 지도와 재작성 대상 지도를 구분
- 지도에서 방·복도·출입구·층 연결을 추출
- 각 방에 기능·위험·분위기 태그 부여
- 장소 설명과 실제 지도 연결이 일치하는지 검증
- 원본 지도 그림을 재사용하지 않아도 게임 맵을 재구성할 수 있도록 좌표·연결 정보 저장

### 4단계 — 인물·세력·세계 상태를 관계 그래프로 연결

- 인물별 목표·비밀·지식·소속·현재 상태 정리
- 세력 간 적대·협력·이용 관계 기록
- 세계 위기 단계와 시간 진행 규칙을 상태 변수로 표현
- 사건 결과가 인물·세력·장소의 상태를 실제로 바꾸도록 연결
- 사망·이탈·구조·배신·도주 이후에도 세계가 진행 가능한지 확인

### 5단계 — 게임 규칙으로 변환

원본의 규칙을 그대로 게임에 옮기지 않는다.

- 원본의 주사위·시간·조우 빈도·위기 규칙을 별도 보존
- 우리 게임의 층·원정·야영·전투당 횟수·자동 진행 규칙으로 변환
- 변환 전후의 차이와 이유를 기록
- 기존 `G.Event`의 조건·선택·판정·결과 구조에 매핑
- 직업이 없거나 판정에 실패해도 진행이 막히지 않는 대체 경로 제공

### 6단계 — 생성기와 검증기 구축

정규화된 DB가 쌓이면 다음 도구를 만든다.

- **Scenario Compiler:** 정규화 레코드를 게임 런타임 형식으로 변환
- **Story Composer:** 인과·선행 조건을 만족하는 사건 묶음을 구성
- **Content Validator:** 끊어진 참조, 도달 불가능한 분기, 누락된 단서, 모순된 조건 검사
- **License Validator:** 상업적 사용이 제한된 자산과 출처 누락 검사
- **Seed Replay:** 동일 시드에서 같은 생성 결과를 재현
- **Scenario Preview:** 생성된 장소·인물·사건·단서 흐름을 개발자가 확인

### 7단계 — 첫 시나리오를 실제 게임에서 검증

- The Old Blood의 일부 미스터리를 작은 지역 콘텐츠로 구현
- 원작의 순서를 그대로 강제하지 않고 플레이어의 행동에 따라 상태가 달라지는지 확인
- 핵심 단서가 우연히 하나도 나오지 않는 상황이 없는지 테스트
- 모든 인물·장소를 반드시 방문해야만 해결되는 구조가 아닌지 확인
- 방치 기본 행동과 직접 개입의 보상 차이가 명확한지 확인
- 반복 생성 시 이름만 바뀐 동일한 이야기로 느껴지지 않는지 플레이 테스트

## 8. 완료 기준과 우선순위

DB의 성공을 레코드 개수로 판단하지 않는다.

| 검증 기준 | 통과 조건 |
|---|---|
| 출처 추적 | 모든 핵심 레코드에 원본 페이지와 출처가 있다 |
| 불확실성 보존 | 원문 모순·미확인 정보가 명시되어 있다 |
| 참조 무결성 | 인물·장소·사건·단서 간 ID 연결이 유효하다 |
| 인과 일관성 | 사건이 선행 조건과 세계 상태를 위반하지 않는다 |
| 단서 공정성 | 핵심 사실에 도달할 수 있는 충분한 대체 경로가 있다 |
| 조합 적합성 | 장소·인물·사건이 공간과 상황에 맞게 연결된다 |
| 진행 가능성 | 실패·방치·이탈·인물 사망 후에도 세계가 멈추지 않는다 |
| 게임 적용성 | 기존 이벤트 엔진이 처리할 수 있는 형태로 변환된다 |
| 라이선스 안전성 | 상업적 사용이 제한된 자료가 빌드에 섞이지 않는다 |
| 재현성 | 같은 입력과 시드에서 생성 결과를 재현할 수 있다 |

**작업 우선순위**

1. Victor 미스터리의 단서·분기·결과 완전 추출
2. 조우 테이블 행 단위 정규화
3. 인물·세력·세계 상태의 관계 연결
4. 지도 공간 구조 데이터화
5. 게임 규칙 변환 및 기존 사건 엔진 연결
6. 자동 검증기와 시나리오 생성기
7. 두 번째 시나리오를 추가해 재사용성이 실제로 성립하는지 검증

두 번째 시나리오를 넣었을 때 첫 번째와 같은 스키마로 처리할 수 없다면, 첫 시나리오에 과도하게 맞춘 DB일 수 있다. 두 번째 원본을 통해 스키마의 범용성을 검증한다.

## 9. 개발 원칙 요약

1. **원본은 보존하고, 게임용 변환은 분리한다.**
2. **콘텐츠 수보다 연결 관계와 인과관계를 우선한다.**
3. **무작위 조합이 아니라 조건을 만족하는 조합을 만든다.**
4. **핵심 단서와 진행에는 대체 경로를 둔다.**
5. **플레이어가 방치하거나 실패해도 세계는 계속 변한다.**
6. **원본의 모순과 불확실성을 숨기지 않는다.**
7. **라이선스는 텍스트·지도·이미지 등 자산별로 확인한다.**
8. **기존 런타임 사건 엔진을 재사용하고 DB는 콘텐츠 공급 계층으로 둔다.**
9. **첫 시나리오를 완전히 검증한 뒤 두 번째 시나리오로 범용성을 시험한다.**
10. **궁극적인 목표는 무한한 랜덤 이벤트가 아니라, 매 원정에 원인과 결과가 있는 새로운 이야기가 생기게 하는 것이다.**
