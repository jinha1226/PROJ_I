# 이벤트 시스템 개발 방향

> 이 문서는 inc/DESIGN.md의 현재 게임 방향을 보완하는 구현 가이드다. 기존 핵심 원칙과 충돌하면 DESIGN.md를 우선하고, 방향이 바뀌면 두 문서를 함께 갱신한다.

## 1. 목표

절차적으로 생성되는 던전에 사건을 연결해, 매 원정이 단순히 다른 지도를 보여주는 데서 끝나지 않고 **다른 판단과 결과를 만드는 경험**이 되게 한다.

게임의 정체성은 자동 진행을 버리고 모든 행동을 수동 조작하는 것이 아니다.

- 평범하고 반복적인 이동·전투·수집은 자동으로 처리한다.
- 결과가 의미 있는 사건에서 플레이어에게 판단 기회를 준다.
- 플레이어가 자리를 비워도 결정 방침과 파티 성향에 따라 진행된다.
- 플레이어의 개입은 더 큰 보상이나 특별한 결과를 노리는 선택이어야 한다.
- 사건의 결과는 원정 일지, 용병의 상태·기벽·관계, 보상과 명성 등 기존 성장 고리로 이어진다.

핵심 문장: **플레이어는 무엇을 감수할지 결정하고, 용병단은 그 결정을 실행한다.**

## 2. 절차적 던전과 이벤트의 결합

이벤트를 지도 생성과 별개의 무작위 목록으로 뿌리지 않는다. 던전 생성 결과에 의미를 부여한 다음, 그 공간에 어울리는 사건을 배치한다.

### 생성 파이프라인

1. **지형 생성** — 방, 복도, 갈림길, 출입구, 보스 구역, 비밀 구역 등 공간 구조를 만든다.
2. **공간 의미 부여** — 각 방과 지점에 roomType 및 tags를 부여한다. 예: crypt, prison, library, altar, treasury, cave, collapsed.
3. **이벤트 후보 필터링** — 공간 태그, 층·깊이, 진행 상태, 파티 구성, 이미 발생한 사건을 기준으로 불가능한 이벤트를 제외한다.
4. **이벤트 슬롯 선정** — 해당 층에서 사건이 발생할 지점을 고른다. 모든 방에 이벤트를 넣지 않는다.
5. **가중치 추첨** — 후보 중 분위기·빈도·중복 방지·최근 사건 유형을 고려해 선택한다.
6. **사건 실행 및 기록** — 선택, 판정, 결과를 세계 상태와 원정 기록에 반영한다.

예시: 감옥 태그가 있는 방은 죄수 구조, 위장한 괴물, 과거 동료, 죄수 간 갈등 등의 후보를 가질 수 있다. 감옥이라는 공간은 사건의 맥락을 제공하고, 실제 사건은 조건과 가중치에 따라 결정한다.

### 기존 맵 생성과의 관계

- 지도 생성 책임은 현재 구조의 js/grid.js에 둔다.
- 이벤트 데이터와 후보 선정은 맵 생성 코드에 과도하게 섞지 않는다. 이벤트 데이터는 데이터 모듈, 후보 선정·상태 관리는 별도 이벤트 로직으로 분리하는 방향을 우선 검토한다.
- 실제 파일 배치와 기존 이벤트 엔진을 먼저 확인하고, 이미 있는 기능을 중복 구현하지 않는다.
- 현재 DESIGN.md에는 같은 시즌의 같은 층이 같은 시드 지형을 재사용하는 설계가 기록되어 있다. **지도 시드 정책을 임의로 바꾸지 않는다.** 지형 시드와 이벤트 시드는 분리할 수 있게 설계해, 지도 재방문 시 사건이 재추첨되거나 결과가 뒤바뀌지 않도록 한다.
- 지형·이벤트 결과를 재현할 수 있도록 시드와 사건 식별자를 기록한다. 이벤트 난수가 지형 생성 결과에 영향을 주지 않도록 독립된 난수 스트림 또는 안정적인 시드 파생 방식을 사용한다.

## 3. 이벤트 유형

초기에는 아래 유형을 사용하되, 유형 자체를 복잡한 클래스 계층으로 만들 필요는 없다. 공통 이벤트 데이터 형식에 태그를 붙이는 정도로 시작한다.

| 유형 | 예시 | 핵심 판단 |
|---|---|---|
| 발견 | 보물, 유물, 비밀 통로, 고대 기록 | 조사할 것인가, 위험을 감수할 것인가? |
| 조우 | 생존자, 상인, 다른 모험가, 정체불명의 존재 | 돕거나 거래할까, 경계하거나 공격할까? |
| 위험 | 함정, 붕괴, 독가스, 저주, 화재 | 안전하게 해결할까, 빠르게 돌파할까? |
| 탐험 | 갈림길, 잠긴 문, 지름길, 미지의 구역 | 안전한 경로와 위험한 보상 중 무엇을 택할까? |
| 파티 | 갈등, 공포, 욕망, 부상, 신뢰 | 누구를 지지하고 무엇을 감수할까? |
| 대형 사건 | 봉인, 의식, 보스의 흔적, 지역 위기 | 지금 개입할까, 준비하거나 물러날까? |

전투 조우와 이야기 이벤트를 구분한다. 몬스터가 나타났다는 이유만으로 매번 선택창을 띄우지 않는다. 일반 전투는 자동 진행하고, 전투 전후에 플레이어의 판단이 실질적으로 달라지는 경우에만 사건으로 승격한다.

## 4. 이벤트 데이터 모델

이벤트는 코드에 하드코딩하기보다 데이터로 정의한다. 아래는 개념 예시이며 실제 프로젝트의 데이터 규약에 맞춰 조정한다.

```json
{
  "id": "wandering_merchant_01",
  "type": "encounter",
  "tags": ["merchant", "underground", "mystery"],
  "conditions": {
    "roomTags": ["cave", "chamber", "corridor"],
    "minDepth": 2,
    "maxDepth": 8,
    "oncePerRun": true
  },
  "weight": 10,
  "choices": [
    {
      "id": "trade",
      "requirements": [],
      "resolution": null,
      "outcomes": ["buy_item"]
    },
    {
      "id": "investigate",
      "requirements": ["perception"],
      "resolution": "ability_check",
      "outcomes": ["reveal_identity"]
    }
  ]
}
```

권장 필드:

- id: 영구적으로 안정된 이벤트 ID.
- type, tags: 유형과 검색용 태그.
- conditions: 층·공간·파티·세계 상태·이전 사건 등 발생 조건.
- weight: 조건을 통과한 후보 사이의 상대 가중치.
- oncePerRun, cooldown, uniqueGroup: 반복·중복 제어.
- choices: 플레이어가 선택할 수 있는 행동.
- requirements: 직업, 능력, 주문, 아이템, 파티 상태 등에 따른 선택지 조건.
- resolution: 능력 판정, 내성 굴림, 자동 성공 등 해결 방식.
- outcomes: 성공·실패·부분 성공에 따른 결과.
- historyKey 또는 사건 상태: 후속 사건과 재방문에서 사용할 기록 키.

**발생 조건(Conditions)과 해결 판정(Resolution)을 분리한다.** 지각이 높은 파티가 함정을 일찍 발견할 수는 있지만, 함정 사건 자체를 무조건 삭제할 필요는 없다. 발견 여부에 따라 경고, 선택지, 피해 위험이 달라지게 한다.

## 5. 플레이어 선택 설계 원칙

### 선택은 실제 비용과 결과가 있어야 한다

선택지는 표현만 다르고 결과가 같은 선택지의 나열이 되면 안 된다. 각 선택에는 보상, 자원 소모, 시간, 부상 위험, 관계 변화, 이후 사건의 변화 중 하나 이상의 실질적인 차이가 있어야 한다.

예시: 고대 제단을 발견했을 때

- 즉시 조사: 빠르지만 함정에 노출될 수 있다.
- 도적에게 조사 지시: 시간이 들지만 위험을 낮출 수 있다.
- 주문 사용: 주문 자원을 소비해 정보를 얻는다.
- 지나치기: 안전하지만 보상을 포기한다.

### 직업은 해결책을 독점하지 않고 유리한 선택지를 제공한다

- 도적이 없어도 함정을 우회하거나 다른 방법으로 조사할 수 있다.
- 성직자는 저주나 언데드에 대한 추가 정보를 얻을 수 있다.
- 바드는 협상에서 유리한 접근을 열 수 있다.
- 마법사는 주문 자원을 사용해 물리적으로 어려운 문제를 해결할 수 있다.

직업·능력은 유일한 정답 열쇠가 아니라 선택의 폭, 비용, 성공 가능성, 결과의 질을 바꾼다. 특정 직업이 없다는 이유만으로 진행이 막히지 않게 한다.

### 방치형 원칙과 일치시킨다

DESIGN.md의 원칙인 **방치는 안전, 개입은 이득**을 유지한다.

- 선택창은 시간제한이 있을 수 있으며, 제한 시간 내 응답이 없으면 사전에 설정한 결정 방침 또는 파티 성향에 따른 기본 행동을 실행한다.
- 기본 행동은 진행을 막지 않고, 대체로 보수적이고 안전해야 한다.
- 개입하면 더 큰 보상, 특별한 정보, 용병의 성장·기벽 등 추가 이득을 노릴 수 있다. 단, 위험과 비용도 명확해야 한다.
- 선택창은 한 화면에 하나의 결정만 보여준다.
- 사소한 문 열기·일반 몬스터 공격·반복 조사마다 묻지 않는다. 방치 중인 플레이어에게 승인 버튼을 연속해서 누르게 만들지 않는다.

### 언제 이벤트를 보여줄까?

- 새 층이나 새로운 구역에서 의미 있는 발견이 있을 때.
- 갈림길, 특수 방, 보물, 위험 지점 등 플레이어가 경로·위험을 판단할 수 있을 때.
- 파티의 상태나 관계가 실제로 달라질 만한 순간.
- 이전 행동의 결과가 돌아오는 순간.

이미 익숙해진 층은 기존 설계대로 빠르게 숫자를 쌓는 구간으로 유지한다. 새 층은 사건과 위기가 생기는 구간으로 삼는다. 이벤트 빈도는 맵의 모든 방을 채우는 방식이 아니라, 층당 의미 있는 사건 슬롯을 제한하는 방식으로 조절한다.

## 6. 사건의 연속성과 기억

독립적인 랜덤 이벤트를 많이 늘리는 것보다, 소수의 사건이 서로 이어지는 편이 더 강한 경험을 만든다.

예시 연속 사건:

1. 상층에서 정체불명의 발자국을 발견한다.
2. 다음 구역에서 부상당한 탐험가를 만난다.
3. 더 깊은 층에서 봉인된 제단과 의식의 흔적을 확인한다.
4. 의식을 방해할지, 준비 후 돌아올지 결정한다.
5. 이전 선택에 따라 보스의 상태, 보상, 생존자의 운명이 달라진다.

연속 사건은 다음 상태를 가질 수 있다.

- 시작 전
- 시작됨
- 단서 발견
- 선택 완료
- 성공·실패·방치·포기
- 후속 사건 대기
- 종료

모든 이벤트가 긴 퀘스트라인일 필요는 없다. 즉시 끝나는 사건, 같은 층 안에서 이어지는 사건, 다음 층으로 이어지는 사건, 다음 원정까지 남는 사건을 섞는다.

사건 결과는 기존 시스템과 연결한다.

- 원정 일지와 사건 기록
- 용병의 긍정·부정 기벽 및 사건 전용 기벽
- 용병 간 신뢰·갈등·관계
- 부상, 사망, 생존, 은퇴
- 금화·보상·명성·유산
- 이후 이벤트의 조건과 선택지

서사를 별도의 대화 수집 시스템으로 만들지 않는다. **사건이 용병과 원정의 상태를 바꾸고, 그 변화가 다음 사건의 조건이 되는 구조**를 우선한다.

## 7. 이벤트 선정 알고리즘

권장하는 단순한 절차:

1. 현재 위치와 층에서 이벤트 슬롯이 있는지 확인한다.
2. 공간 태그가 맞는 이벤트만 남긴다.
3. 층·진행도·파티·사건 이력 조건을 적용한다.
4. 이미 발생했거나 쿨다운 중인 이벤트를 제외한다.
5. 최근에 자주 나온 유형은 가중치를 낮춰 반복감을 줄인다.
6. 남은 후보 중 가중치 추첨을 한다.
7. 후보가 없으면 이벤트를 억지로 생성하지 않고 일반 탐험을 계속한다.

주의:
- 가중치는 확률 보장이 아니라 상대적 선택 비율이다.
- 파티 직업이 특정 이벤트를 너무 자주 불러내지 않도록 출현 빈도와 선택지 해금 조건을 구분한다.
- 동일한 방·층·시드에서 결과를 재현할 수 있도록 이벤트 선택 결과를 저장한다.
- 이벤트 후보가 없는 경우를 정상 상태로 취급한다. 억지로 부적합한 이벤트를 배치하지 않는다.

## 8. 초기 콘텐츠 범위와 검증

처음부터 수백 개를 만들지 않는다. 데이터 형식과 루프가 재미있는지 확인할 수 있는 작은 수직 단면을 먼저 만든다.

### 1차 이벤트 묶음: 20개

| 유형 | 수량 | 검증할 것 |
|---|---:|---|
| 발견 | 4 | 조사와 보상 사이의 위험 선택 |
| 조우 | 4 | 대화·거래·구조·경계 |
| 위험 | 4 | 능력 판정과 피해·자원 비용 |
| 탐험 | 3 | 경로·시간·보상 선택 |
| 파티 | 3 | 용병 성격·관계·기벽 변화 |
| 대형 사건 | 2 | 여러 단계의 사건 연결 |

20개는 최종 콘텐츠 목표가 아니라 시스템 검증용 샘플이다.

- 파티 구성이 달라지면 선택지나 해결 방식이 달라지는가?
- 직업이 없어도 대체 경로로 진행할 수 있는가?
- 시간제한 동안 방치했을 때 기본 방침대로 안전하게 진행되는가?
- 같은 이벤트가 짧은 간격으로 반복되지 않는가?
- 사건 결과가 일지·용병 상태·성장에 실제로 반영되는가?
- 이벤트가 너무 잦아 자동 진행의 장점을 해치지 않는가?

### 관찰 지표

- 층당 선택창 수와 선택창을 본 시간 비율
- 이벤트 유형별 발생 빈도와 반복률
- 플레이어가 직접 개입한 비율과 기본 방침으로 처리된 비율
- 선택지별 선택률 및 결과 차이
- 사건으로 발생한 부상·사망·보상·기벽 변화
- 플레이어가 기억하는 사건과 다음 원정을 시작하는 이유

승률이나 이벤트 발생 수만으로 재미를 판단하지 않는다. 플레이어가 선택의 위험과 보상을 이해했는지, 결과가 기억에 남는지, 방치형 흐름을 방해하지 않는지를 함께 확인한다.

## 9. 개발 순서

1. 기존 이벤트·선택창·시간제한·결정 방침 코드와 맵 생성 코드를 조사한다.
2. 현재 데이터 구조에 맞춰 이벤트 공통 스키마와 조건 평가기를 정한다.
3. 공간 태그와 이벤트 슬롯을 연결한다.
4. 발견·위험·조우 유형에서 각 1~2개씩 먼저 구현한다.
5. 판정, 선택 결과, 방치 기본 행동, 사건 기록을 연결한다.
6. 20개 이벤트로 확장하고 반복·확률·진행 흐름을 검증한다.
7. 사건 연계와 파티 상태 기반 분기를 추가한다.
8. 실제 플레이 테스트 결과를 반영해 빈도와 보상 위험을 조정한다.

**우선순위는 이벤트 수가 아니라 이벤트 한 건이 플레이어의 판단과 원정의 결과를 얼마나 의미 있게 바꾸는지다.**
